# JUNCTION CHINA 2026 智能穿戴赛道 · 标准对照与改造清单

> 仅分析/规划，本轮不改代码、不提交。
> 依据：赛事 Brief（ARUI · 自动化 · 多模态，100 分制，模拟器实际运行核验）。

## 0. 一句话结论

当前 MemoryLens 的优势在**识别与会议后端**；但赛事要的是**在 AR 模拟器里跑通的智能体闭环**：

```text
语音/文本输入 → 理解 → 信息处理/工具操作 → 自动生成/更新 ARUI → 确认/纠错 → 五状态可观察
```

我们现在只有“识别结果卡片 + 控制台/会议后端”，缺：

- 眼镜端真正的**文本输入**与**语音/文本同一任务**；
- **待命/处理中/待确认/完成/异常**五状态；
- **两次连续调整**（内容变化 + 重点/布局变化）；
- **独立纠正**与上下文保持；
- **旧结果作废**、**延迟测量**、**8 项验收用例**；
- 冻结包、2 页 PDF、120 秒视频、证据索引。

## 2. 推荐场景：会议行动项 AR 助手

赛事参考场景就是“会议文本 → 行动项 → 文本调整显示”。我们已有会议分离/转写/人物库，天然契合，且比纯“认人卡片”更像智能体。

### 演示脚本（3 分钟，覆盖评分点）

1. **待命**：眼镜空屏显示“说『整理会议待办』或输入指令”。
2. **语音新需求**：用户说“整理今天会议的待办，按负责人分组”。
   → **处理中**：“正在理解会议…提取行动项…”
   → 完成：HUD 出 4 条 `负责人 / 事项 / 截止 / 状态`。
3. **第一次调整（内容）**：语音/文本“只看待确认的，王姐的排前面”。
   → 列表筛选 + 重排；保留上下文（还是同一场会）。
4. **第二次调整（重点/布局）**：文本“只保留负责人和截止时间”。
   → 切换紧凑布局，字段减少、行高重排。
5. **跨方式 + 纠正**：文本“第 2 条负责人不是王姐，是里奥”。
   → 只改第 2 条，其余上下文不变；HUD 标注“已纠正”。
6. **待确认**：显示“3 条待保存，确认后写入会议记录”；按确认才保存。
7. **完成**：“已保存 3 条行动项 · 可回看”。
8. **异常**：注入模型超时 → 显示“模型超时（注入测试），按确认重试”，旧结果不冒充新结果。

### 五状态映射

| 赛事状态 | 眼镜 HUD |
|---|---|
| 待命 | `说指令 / 文本输入` |
| 处理中 | `正在整理会议…` + 进度点 |
| 待确认 | `找到 4 项，3 项待确认；确认保存` |
| 完成 | `已保存 3 项 / 已更新` |
| 异常 | `模型超时（注入测试）· 确认重试` |

## 5. 多模态与上下文设计

- **文本入口**：`takeTextInput()` 返回完整 UTF-8；需在 manifest 声明 `input.text`，Host 2。
- **语音入口**：现有 `requestVoiceInput` + ASR；语音结果只作为文本命令的一种来源，**不把 ASR 当第二交互方式**。
- **统一命令对象**：

```json
{
  "requestId": 7,
  "meetingId": "s_xxx",
  "source": "voice|text",
  "text": "只看待确认的，王姐的排前面",
  "context": {"lastItems": ["..."], "selected": 2}
}
```

- **纠正**：解析成 `update_item(index, field, newValue)`，只改指定项，其余上下文保留。
- **旧结果**：后端返回 `requestId`；眼镜只接受当前 `requestId`，旧响应丢弃并标 `stale`。
- **确认**：写库/保存行动项属于敏感动作，必须“待确认”状态二次确认。
