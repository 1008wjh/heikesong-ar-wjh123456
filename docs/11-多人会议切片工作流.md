# 多人会议「连续录音 + 多次切片」工作流设计（待适配）

> 来源：产品/交互方 2026-11-07 提出的工作流规则。
> 状态：**设计评审 + 落地映射**；本轮不改代码、不提交，等重新拉取最新仓库后按本文适配。

## 0. 结论

这套设计是合理的，尤其两点和现有实现天然契合：

1. **单确认键 + 状态路由**：不新增按键，靠"当前是否有待查看的简略结果"切换职能，符合眼镜只有 6 个离散动作的硬约束。
2. **先聚类分人、后逐人声纹比对**：正是 `src/diarize.py` 的现有顺序；而且"以整段有效音色为单位"比当前逐句 embedding 更稳，能减少身份跳变。

需要补三个工程约束，否则规则本身成立、实现会踩坑：

| 约束 | 原因 | 处理 |
|---|---|---|
| `input.audio` 单会话最长 60 秒 | SDK 硬限制；"全局主录音"不能是一个永不结束的 session | 逻辑录音连续，物理上每 ~45s 自动 `finish()` 并立刻重开 session；应用层拼接 PCM，切片时间轴连续 |
| 切片音频怎么给后端 | 若同时上传"主录音分片"和"切片音频"会重复占带宽/磁盘 | **主录音分片持续上传**（带时间轴），切片只传 `{start,end}`，后端从已上传音频里截取 |
| 简略结果与详情分两次返回 | 规则要求二次确认才给身份 | 后端一次算完并存档，**summary 接口只回人数/熟人陌生人计数**；details 接口才回身份 |

## 1. 状态机（眼镜端）

| 状态 | 屏幕 | 确认键 | 返回键 |
|---|---|---|---|
| `MEET_RECORDING` | 会议录制中 · 已录 Xs · 已切 N 段 | **提交切片**（从上次切片点到当前），进入 `MEET_PROCESSING` | 停止主录音 → `MEET_ARCHIVING` |
| `MEET_PROCESSING` | 分析中…（主录音仍在跑） | 忽略并提示"上一段还在分析"（或排队，见决策 D3） | 同 `MEET_RECORDING` |
| `MEET_SUMMARY` | 本段识别到 N 人（熟人 X / 陌生 Y），按确认看详情 | **查看详情** → `MEET_DETAIL` | 回到 `MEET_RECORDING`（摘要收起，主录音继续） |
| `MEET_DETAIL` | 逐个说话人详情（姓名/身份/资料） | 下一个说话人；最后一个之后 → `MEET_RECORDING` | 回到 `MEET_SUMMARY` |
| `MEET_ENROLL` | 陌生人建库（复用单人口述流程） | 沿用单人识别的确认逻辑 | 取消，回 `MEET_DETAIL` |
| `MEET_ARCHIVING` | 正在归档… | 忽略 | 忽略 |
| `MEET_DONE` | 会议已保存 · N 段 / M 人 | 回 idle | 回 idle |

关键点：

- "查看详情"期间**主录音继续**；用户看完详情后，下一次切片起点仍是"上一段切片终点"，中间看详情的时间会算进下一段（不会丢音频）。
- 详情里的陌生人建库是**嵌套状态**：确认键此时先给"录音/保存"用，不触发切片；建库结束自动回 `MEET_DETAIL`。
- 所有切片状态独立：`slice.seq` 单调递增，`status` 独立；前端只展示当前一段的摘要/详情。

## 2. 后端接口（在现有 `/api/v1` 上增加）

现有：`session/create`、`audio/upload`、`session/{id}/finalize`、`bind`、`transcript`、`audio/play`、`session/{id}`。

新增/调整：

| 方法 | 路径 | 入参 | 返回 |
|---|---|---|---|
| POST | `/api/v1/session/{id}/slice` | `{start, end}`（秒；start 默认上次 end） | **仅摘要**：`{seq, start, end, speaker_count, known, unknown, dropped_overlap}`；不返回姓名/档案 |
| GET | `/api/v1/session/{id}/slice/{seq}` | — | **详情**：`{seq, speakers:[{spk_id, person_id?, name?, similarity, seconds, segments:[...]}], transcript}` |
| GET | `/api/v1/session/{id}/slices` | — | 切片列表（seq/起止/摘要计数/状态） |
| POST | `/api/v1/session/{id}/archive` | `{title?}` | 归档为一条会议记录：完整音频 + 全部切片 + 时间 + meeting_id |
| POST | `/api/v1/audio/upload` | 已有，保持"主录音分片"语义 | 继续用；切片前前端先 flush 到当前时刻 |

数据模型（`data/meetings/<id>/meta.json`）：

```json
{
  "sessionId": "s_xxx",
  "meetingId": "m_xxx",
  "status": "recording|archived",
  "recordedSeconds": 128.4,
  "slices": [
    {
      "seq": 1, "start": 0.0, "end": 18.2, "status": "done",
      "summary": {"speaker_count": 4, "known": 2, "unknown": 2, "dropped_overlap": 0},
      "speakers": [
        {"spk_id": "spk_0", "person_id": "p_x", "name": "王姐",
         "similarity": 0.93, "seconds": 8.1, "segments": [[0.2, 4.1], [10.5, 14.7]]}
      ],
      "transcript": [{"start": 0.2, "end": 4.1, "spk_id": "spk_0", "text": "..."}]
    }
  ]
}
```

> 当前仓库是 JSON 文件而不是 MySQL；"存数据库会议表"落地为 `meta.json` 的 `status:"archived"` 记录。
> 如果必须 MySQL，再加一个 `meeting` 表适配层，不动上层 API。

## 3. 处理流水线（每个切片）

```text
切片音频（从主录音分片按 start/end 截取）
  → pyannote 分段（沿用 diarize）
  → 逐段 CAM++ 聚类（沿用 diarize）
  → 按 spk 合并该人所有有效段，拼成"整段音色"
  → 每个 spk 只做一次 1:N 声纹比对（满足约束 4.1）
  → 得到 person_id/name/similarity
  → 先写 details，再只把计数返回给 summary
  → 可选：对该切片逐段 ASR（llm.transcribe），文字进 details
```

需要改 `src/diarize.py` 的地方：

- 新增 `per_speaker_embedding=True` 选项：聚类后按 spk 合并段，重新 `voice.embed`，再做 `voice.match`；当前是"逐段 embedding 的簇质心"。
- 返回 `speakers[].segments`，供详情/回放。
- 重叠策略保持 `drop/trim`；摘要里带 `dropped_overlap`。

## 4. 眼镜端"全局主录音"实现

```text
逻辑录音（meeting.recording=true）
  ├─ 物理 session A（0-45s）→ finish
  ├─ 物理 session B（45-90s）→ finish
  └─ ... 每次 end 立即重开，PCM 追加到 meeting buffer
```

- 每 ~5s 把新增 PCM 封成 wav 分片 `POST /audio/upload`（seq 递增），服务端累计时间轴。
- 用户提交切片前：先把 buffer 里未上传的部分 flush，再 `POST /slice {start,end}`，服务端保证音频已齐。
- 切片分析期间录音继续；`MEET_PROCESSING` 时确认键忽略。
- 返回/结束：停止 session → flush → `POST /archive` → 显示"会议已保存"。
- 断网/后台：录音继续本地缓存；恢复后补传（可作为后续增强）。

## 5. 需要你拍板的 3 个决策

| 编号 | 决策 | 选项 | 建议 |
|---|---|---|---|
| D1 | 切片音频来源 | A. 主录音分片持续上传 + `{start,end}` 截取（推荐，省带宽/磁盘）<br>B. 每次切片单独上传音频（实现简单，但主录音和切片重复） | **A** |
| D2 | 详情展示方式 | A. 每次确认看一个说话人，最后一个之后复位（符合"逐个返回"）<br>B. 一次列全部，自动滚完再复位 | **A** |
| D3 | 分析未完成时再按确认 | A. 忽略 + 提示"分析中"（简单、不会乱序）<br>B. 排队下一段（体验好，但状态复杂） | **A**（Demo 优先） |

## 7. 验收标准

- 提交切片返回 **只有计数**，详情接口才含姓名/档案；
- 同一 spk 在一个切片内只做一次声纹检索；
- 连续录音跨 session 无丢失（累计时长与切片 end 一致）；
- 摘要→详情→复位→下一片，状态不串；
- 返回后会议记录包含完整音频、meeting_id、全部切片；
- 现有 27/55/17/13 等测试不回归。
