## 1. 兜底与日志

**模型调用层（llm.py）**

- 退避重试：超时 / 连不上 / 408 / 429 / 5xx 重试，默认 2 次（`AR_LLM_RETRIES`），
  400 这类配置错误直接失败不重试；
- JSON 校验：推荐和要点两个结构化接口都会解析 JSON；不合法就带一句
  “上一次不是合法 JSON，请只输出 JSON”再问一次；
- 彻底失败：
  - 提词 → 返回规则兜底三条（用这段的要点，没有就给三句通用接话），标记 `degraded`，
    界面显示「模型暂时出问题，先用规则兜底」；
  - 要点 → 回退关键词规则（原有能力），日志里记 `llm.fallback`；
  - 语音转写失败 → 界面显示「这段没听清 / 再说一遍，或用手打」，不再是空白；
- 连接复用：有 `requests` 就用 `Session`（省 TLS 握手），没有就退回 urllib。

**日志**

每次模型调用写一行 `llm.call`：`tag(analyze/recommend/classify)`、`attempt`、`ok`、
`ms`、`model`、错误码/错误摘要；兜底写 `llm.fallback`。`GET /api/agent/log?n=50` 能看到：

```json
{"kind":"llm.call","tag":"recommend","ok":true,"ms":1021}
{"kind":"agent.feed","total":1487,"asr_ms":399,"llm_ms":0,"rec_ms":941}
```

`/api/agent/status` 多返回一份统计：

```json
"stats": {"calls":12,"failures":0,"retries":0,"fallbacks":0,"last_ms":1021,"last_error":""}
```

读接口 `do_GET` 也加了统一异常捕获，出错返回 JSON 而不是断开连接（写接口原来就有）。

## 2. 4.1 秒到底慢在哪

实测拆解（王姐 6.8 秒音频，按「提词」）：

| 阶段 | 冷启动第一次 | 热态 |
|---|---|---|
| ASR | 2351–3167ms（含模型加载 ~1.3s） | 170ms 独立跑 / 380ms 服务内并发 |
| 要点抽取（第二次模型调用） | ~700–1000ms | 同左 |
| 提词生成 | ~900ms（偶发 2.7s） | 同左 |

结论：**不是模型特别慢，是三条叠加**——ASR 冷加载 + 每次都跑两次模型（先抽要点、再出提词）。
所以先做不改变效果的减法：

| 措施 | 效果 |
|---|---|
| 启动时预加载 ASR（原来只预热了声纹/分轨） | 第一次提词不再多等 ~1.3s |
| 提词跳过“要点抽取”这次模型调用（用关键词规则） | −700~1000ms |
| 待办/以前不再调模型（render 里本来就是确定性分支） | −900ms |
| 以前连要点抽取也跳过（只看档案） | 0.5s 返回 |
| 连接复用 + max_tokens 200→160 | −100~200ms |

实测（同一台机、热态）：

```
hint1  1213ms   hint2 1305ms   hint3 1502ms
todo1  1286ms   todo2 1756ms
recall 525ms / 503ms
```

## 3. 还能更快，但有取舍（等你拍板）

| 方案 | 预计收益 | 风险 |
|---|---|---|
| 把“抽要点 + 出提词”合并成一次模型调用 | −400~700ms | 提示词变复杂，JSON 结构要重测；质量可能波动 |
| 换更快的模型档位（qwen-turbo / glm-flash 之类） | −300~600ms | 要测质量和中文自然度，key 另配 |
| 渐进式出结果：先推规则三条，模型回来再覆盖 | 首屏 <300ms | 镜片会闪一次（二次推送），演示时可能被当成卡顿 |
| 录音时边转写边预生成 | 理论最快 | 客户端目前只在按键时发音频，做不了；要改眼镜端 |
| 本地小模型（1.5B 级） | 延迟低 | 中文质量风险大，不建议 |

前两项是低风险的，后两项要动交互/客户端。要上哪个你说一声。
